# Design

## Context

Мотивация — в `proposal.md` (Why), требования — в `specs/contact-list/spec.md` и `specs/contact-card/spec.md`.

Как устроено сейчас:

- `src/app/page.tsx`: серверный `Directory` внутри `Suspense` читает `searchParams.added` и вызывает `listContacts()` (`src/lib/contacts.ts`). Тот отдаёт **все** контакты (`id, name, howWeMet, phone, email`), отсортированные по `name collate "ru-RU-x-icu", id`, без `limit`.
- `src/components/contact-directory.tsx` (клиентский): получает весь массив, фильтрует его в браузере (`normalizeForSearch` / `toSearchWords` / `matchesAllWords` из `src/lib/search.ts`), группирует по букве (`groupByLetter`), показывает счётчик, «Никого не нашли», подсветку `highlightId` и прокрутку к нему. Поиск — локальный `useState`, в адресе его нет.
- После создания контакта `new-contact-dialog.tsx` делает `router.replace("/?added=<id>")`.
- `BackLink` (`src/components/back-link.tsx`) — серверный `Link href="/"`. `DeleteContactButton` после удаления делает `router.replace("/")`.
- Серверные действия после записи вызывают `revalidatePath("/")`.
- `next.config.ts`: `cacheComponents: true`, `partialPrefetching: true`. Данные из базы читаются внутри `Suspense`. Перед кодом — гайды в `node_modules/next/dist/docs/` (правило `AGENTS.md`). В частности, `<Link>` по умолчанию сохраняет позицию прокрутки, пока страница видна (`03-api-reference/02-components/link.md`, раздел `scroll`).
- UI: shadcn/ui `base-nova` поверх `@base-ui/react`, компонента `pagination` нет.
- Тестовые данные `pnpm db:seed` — 1000 контактов: 20 страниц при 50 на странице, 40 при 25, 10 при 100.
- Автотестов в проекте нет: проверка — `pnpm typecheck`, `pnpm lint`, `pnpm build` и руками.

## Goals / Non-Goals

**Goals:**

- Главная отдаёт в браузер не больше выбранного количества строк списка, максимум 100. Вес HTML главной на 1000 контактах падает в разы.
- Сортировка, поиск и разбивка на страницы — в одном месте, в запросе к базе. Браузер ничего не фильтрует.
- Правила поиска для пользователя не меняются: все слова, любой порядок, регистр не важен, «ё» = «е».
- Без новых npm-библиотек и без миграций.

**Non-Goals:**

- Ускорение карточки контакта и блока «Пора мстить»: их не трогаем.
- Индексы под поиск (`pg_trgm`) и под сортировку: для тысяч строк не нужны.
- Произвольное количество на странице: только 25, 50 или 100.
- Хранение выбора на сервере или в базе: у каждого браузера свой выбор.

## Decisions

### 1. Разбивка на страницы — `limit/offset`, а не «курсор»

`listContactsPage({ page, pageSize, words })` в `src/lib/contacts.ts`:

1. Один запрос считает оба числа: `count(*)` — всего контактов, `count(*) filter (where <совпадение>)` — найдено (без поиска совпадает со «всего»).
2. `pageCount = max(1, ceil(matched / pageSize))`, номер страницы зажимается в `[1, pageCount]`. Это даёт «слишком большой номер → последняя страница» без редиректа.
3. Второй запрос — строки: тот же `where`, `order by name collate "ru-RU-x-icu", id`, `limit pageSize offset (page - 1) * pageSize`.

Возвращает `{ contacts, totalCount, matchedCount, page, pageCount }`. Допустимые размеры `PAGE_SIZES = [25, 50, 100]` и `DEFAULT_PAGE_SIZE = 50` лежат в `src/lib/pagination.ts`. Запрос сам размер не выбирает, а получает уже проверенный (решение 4).

- Альтернатива: курсор («после такого-то имени»). Отклонено: спека требует номера страниц и переход сразу на «20», а курсор умеет только «следующая/предыдущая».
- `id` в сортировке — для полных тёзок: без него порядок одинаковых имён между запросами не гарантирован, и человек мог бы «перепрыгнуть» со страницы на страницу.
- `listContacts()` удаляем: после замены он нигде не используется.

### 2. Поиск — в SQL, с теми же правилами

- Слова запроса готовит прежний `toSearchWords` (нижний регистр, «ё» → «е», разбивка по пробелам), он работает и на сервере.
- Совпадение для каждого слова: `replace(lower(name collate "ru-RU-x-icu"), 'ё', 'е') like '%' || слово || '%'`. Слова соединены через `and`. `lower` с ICU-правилом сравнения переводит кириллицу в нижний регистр одинаково на любой ОС: на сервере Postgres на Alpine, локально — свой образ.
- Символы `%`, `_` и `\` в словах экранируются (`escapeLike` в `src/lib/search.ts`): иначе запрос «%» нашёл бы всех.
- `matchesAllWords` и фильтрация в `ContactDirectory` удаляются.
- Альтернатива: оставить фильтр в браузере, а на сервер отдавать только «лёгкий» список имён. Отклонено: это всё равно весь список в каждой загрузке, и при росте базы проблема вернётся.

### 3. Состояние — в адресе: `?page=`, `?q=`, `?size=`

- `page.tsx` читает `page`, `q`, `size` и `added` из `searchParams` (если значение пришло массивом — берём первое). В новом `src/lib/pagination.ts` неправильные значения обезвреживают две функции:
  - `parsePage` превращает неправильный номер («abc», «0», «-3») в 1;
  - `parsePageSize` возвращает число только для 25, 50 или 100, иначе `null`.
- Ссылки строит один помощник `buildListHref({ q, page, size })`. В адрес не пишутся `page` на первой странице, `size` при 50 и пустой `q`.
- Почему адрес, а не состояние в браузере: страница рендерится на сервере, и ей нужно знать номер, запрос и размер. Плюс закладки, «Назад» и одинаковые контакты по одной ссылке в любом браузере (спека «Страница, поиск и количество в адресе») даёт сам адрес.

### 4. Количество на странице: адрес → запомненный выбор → 50

- **Откуда берётся.** `Directory` вычисляет размер так: `parsePageSize(searchParams.size) ?? parsePageSize(cookie) ?? DEFAULT_PAGE_SIZE`. Cookie читается через `cookies()` из `next/headers` внутри того же `Suspense`: главная и так динамическая из-за `searchParams`.
- **Где запоминается — cookie `contact-list-size`** (`path=/`, `max-age` — год, `SameSite=Lax`). Значение — только число. Записывает его браузер (`document.cookie`) по нажатию на число в выборе, до перехода. Ссылка с `?size=` cookie не трогает: запоминается только нажатие (спека «Запоминание количества»).
  - Альтернатива: `localStorage`. Отклонено: сервер его не видит. Главная сначала пришла бы по 50, а потом перестроилась бы на 100 — лишняя загрузка и «прыжок» списка.
  - Альтернатива: только адрес. Отклонено владельцем: выбор должен запоминаться.
  - Альтернатива: серверное действие, которое ставит cookie. Отклонено: лишний запрос, а значение не секретное, и записать его может сам браузер.
- **Почему `size` в адресе, даже если выбор запомнен.** Ссылка `/?page=3`, скопированная в браузере, где запомнено 100, открылась бы в другом браузере по 50 и показала бы других людей. Поэтому `buildListHref` всегда пишет `size`, если он не 50, а адрес без `size` значит «как запомнено в этом браузере».
- **Выбор — новый `src/components/page-size-picker.tsx`.**
  - Подпись «По:» и три ссылки `next/link` с `scroll={false}`. Каждая ведёт на `buildListHref({ q, page: pageForSizeChange(page, size, newSize), size: newSize })`.
  - По нажатию — записать cookie и прокрутить к началу списка, как переключатель (решение 6).
  - Группа с `aria-label="Сколько показывать на странице"`, у выбранной ссылки `aria-current="true"`.
  - Не рисуется, если `matchedCount <= PAGE_SIZES[0]`.
- **Место — строка счётчика** в липкой шапке списка: слева счётчик, справа выбор (`flex justify-between`). На телефоне числа визуально компактные, чтобы строка не стала выше, а область нажатия у каждого расширена до 44×44 псевдоэлементом. Самая длинная строка — «Найдено: 120 из 1000» и выбор — помещается в 343 px.
- **Страница после смены размера:** `pageForSizeChange(page, oldSize, newSize) = floor((page - 1) * oldSize / newSize) + 1` в `src/lib/pagination.ts`. Первый контакт текущей страницы (номер `(page - 1) * oldSize + 1`) попадает на новую страницу. Если она окажется больше последней, её зажмёт решение 1.

### 5. Ввод в поиске → адрес

`ContactDirectory` держит текст поля в локальном состоянии (чтобы буквы появлялись сразу) и через 300 мс после последней клавиши переходит на `buildListHref({ q, page: 1, size })` внутри `startTransition`, с `scroll: false`.

- **История:** если поиска не было, а теперь он есть, — `router.push` (новая запись). Если меняется текст уже идущего поиска — `router.replace`. Поэтому «Назад» возвращает к тому, что было до поиска, и не перебирает буквы. Очистка (крестик, Esc) — сразу, без паузы, через `router.push` на `buildListHref({ page: 1, size })`.
- **Синхронизация поля с адресом:** если `q` в адресе изменился не из-за ввода (кнопка «Назад», ссылка «Весь список»), поле получает значение из адреса. Последний отправленный запрос хранится в `ref`: ответ на собственный ввод не перетирает буквы, набранные за это время. Тот же приём «поправить состояние при смене пропса», что уже стоит для `highlightId`.
- **Ожидание:** пока переход в процессе (`isPending` из `useTransition`), список получает `opacity-60` и `aria-busy`. Навигация — это transition, поэтому React показывает прежний список, а не fallback `Suspense`. Для переходов по ссылкам переключателя и выбора размера то же даёт `useLinkStatus` или общий `startTransition` (выбрать по гайду `Link` в `node_modules/next/dist/docs/`).

### 6. Переключатель страниц

- Компонент shadcn `pagination` добавляется через CLI (`pnpm dlx shadcn@latest add pagination`). Это файл в `src/components/ui/` на `buttonVariants` и `lucide-react`, новых зависимостей нет. Ссылки страниц рендерятся как `next/link`, чтобы переход был без перезагрузки. Если версия `base-nova` рисует `<a>`, подключаем `Link` через проп `render` либо обёрткой.
- Новый `src/components/contact-pagination.tsx` строит номера чистой функцией `getPageItems(current, pageCount, siblings)` → `(number | "ellipsis")[]` в `src/lib/pagination.ts`. Правила: всегда первая и последняя, текущая ± `siblings`. Пропуск ровно в один номер показывается номером, а не многоточием («‹ 1 2 3 … 20 ›»). Ссылки — `buildListHref({ q, page: n, size })`.
- Компьютер (`siblings = 1`) и телефон (`siblings = 0`) — два набора номеров, переключаются классами `hidden sm:flex` / `sm:hidden`. Без JS-проверки ширины экрана нет расхождения между сервером и браузером при гидратации. Максимум кнопок: 9 на компьютере, 7 на телефоне. 7 × 44 px с промежутками помещаются в 343 px — это 375 px минус поля по 16 px.
- Стрелки на краях — не ссылки, а неактивные элементы с `aria-disabled`. Текущая страница — `aria-current="page"`. Весь блок — `nav` с `aria-label="Страницы списка"`. Под ним — «Страница N из M».
- **Прокрутка:** у ссылок `scroll={false}`, по нажатию начало списка (обёртка над строкой поиска) прокручивается вверх экрана через `scrollIntoView({ block: "start" })`. Иначе `<Link>` оставил бы экран внизу, у переключателя, а прокрутка Next «к началу страницы» увела бы к блоку «Пора мстить». Та же функция прокрутки используется в выборе размера.
- Переключатель не рисуется, если `pageCount === 1`, и не рисуется на «Никого не нашли».

### 7. Страница с новым контактом

`findContactPage(id, pageSize)` в `src/lib/contacts.ts` считает, сколько контактов стоит раньше по тому же порядку `(name collate "ru-RU-x-icu", id)`, и возвращает `floor(before / pageSize) + 1`. Если контакта нет, возвращает `null`. В `page.tsx`: если есть `added`, а `page` в адресе нет, номер берётся из `findContactPage` с размером из решения 4. Поиск при этом не применяется: диалог и так переходит на `/?added=<id>` без `q`. Подсветка и прокрутка к строке — прежние.

### 8. Возврат из карточки — запоминаем адрес списка во вкладке

- Новый `src/lib/list-return.ts` (клиентский): `rememberListHref(href)`, `readListHref()` и хук `useListHref()` на `useSyncExternalStore`. Для сервера значение `"/"`. Значение лежит в `sessionStorage` под ключом `contact-list-href`, все обращения в `try/catch`: недоступное хранилище даёт `"/"`.
- `ContactDirectory` при каждом показе записывает канонический адрес текущего вида: `buildListHref({ q, page, size })`, без `added`.
- `BackLink` становится клиентским и берёт `href` из `useListHref()`. `DeleteContactButton` делает `router.replace(readListHref())`. Если страница после удаления стала лишней, её зажимает сервер (решение 1).
- Альтернатива 1: передавать адрес списка в ссылке на карточку (`/contacts/42?from=…`). Отклонено: адреса карточек становятся длинными, а закладка на карточку уносит устаревшую страницу.
- Альтернатива 2: `router.back()`. Отклонено: если карточку открыли из закладки, «назад» уведёт из приложения, а удаление должно заменять запись истории, а не возвращаться по ней.

### 9. Что остаётся как есть

- `revalidatePath("/")` в действиях: главная динамическая, свежими становятся все варианты `?page` / `?q` / `?size`.
- Группы по букве (`groupByLetter`) считаются по контактам текущей страницы. Заголовок буквы вверху страницы при «продолжении» буквы получается сам.
- `DirectorySkeleton` — только для первой загрузки.
- Тексты счётчика («1000 контактов», «Найдено: N из M») и «Никого не нашли» — прежние, но числа приходят с сервера.

## Risks / Trade-offs

- [Поиск больше не мгновенный: пауза 0,3 с и запрос на сервер] → Буквы в поле появляются сразу, список при ожидании бледнеет, так что видно, что поиск идёт. Пауза — одна константа, её легко подстроить.
- [«Назад» после смены количества 50 → 100 возвращает прежнюю страницу уже по 100: в старом адресе нет `size`, и действует запомненный выбор] → Согласовано владельцем как известное ограничение (решение 13 в `proposal.md`). Исправление — писать `size` в адрес всегда, а не только когда он не 50. Это делает адреса длиннее, поэтому отложено.
- [`like` по ICU-строке может отказаться работать, если правило сравнения недетерминированное] → `ru-RU-x-icu` детерминированное, `like` с ним работает. Если на какой-то версии Postgres будет ошибка — добавить `collate "C"` к результату `replace(...)`: на совпадение это не влияет.
- [`offset` медленнеет на десятках тысяч строк] → Для личного списка нереально. Если понадобится — индекс по `(name collate "ru-RU-x-icu", id)`, это отдельное изменение.
- [Ctrl+F ищет только по текущей странице] → Принято: в предложении (решение 8). Поиск по всем — полем «Найти по имени».
- [Контакт добавили или удалили в другой вкладке между запросами — строки «съезжают» на соседнюю страницу] → Пользователь один, последствие — один контакт показан дважды или пропущен до следующей загрузки. Приемлемо.
- [`sessionStorage` или cookie недоступны (строгий приватный режим, запрет cookie)] → `try/catch`: «Весь список» ведёт на первую страницу, а размер без cookie — 50 или из адреса. Выбор в такой вкладке работает, но не запоминается.

## Migration Plan

- Миграций нет: база не меняется. Выкатка обычная: PR → merge в main → образ → миграции (пустой шаг) → новый образ → smoke `/health`.
- Откат — ручной, на предыдущий образ по README. Совместимость с базой полная, потому что схема та же. Cookie `contact-list-size` старая версия просто не читает.
- Старые адреса `/` и `/?added=<id>` продолжают работать.

## Open Questions

- Нужен ли индекс под сортировку, если контактов станет больше 10 000. Решать по факту, на спеки и задачи не влияет.
