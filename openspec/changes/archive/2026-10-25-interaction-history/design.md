# Design

## Context

Зачем — в `proposal.md` (Why), требования — в `specs/`. Решения взяты из `new-features-and-keep-in-touch/design.md` и сокращены: здесь только история мести, без частоты и блока «Пора мстить».

Макет: https://claude.ai/artifact/H3fwWd1z31MDDyrMqBkwNW. Карточка — артборды `Card` / `Card-phone` (копии в `openspec/changes/archive/2026-10-25-contact-card-read-mode/mockups/Card*.dc.html`): по ним сверять раздел «Последняя месть» и строку «мстили …»; строку «Как часто припоминать» в этой фиче не рисуем. Окна — артборды `Record*` («Отомстил»), `History*` («История мести» со всеми видами) и `Delete-record*` (подтверждение удаления записи). При расхождении с текстами спек правы спеки.

Что есть сейчас:

- Одна таблица `contacts` (`src/db/schema.ts`): `name`, `how_we_met`, `phone`, `email`, `notes`, `created_at`, `updated_at`. Миграции Drizzle лежат в `drizzle/` (сейчас одна, `0000_create_contacts`); при выкатке их применяет разовый контейнер (`scripts/migrate.mjs`). Drizzle выполняет все новые миграции в одной транзакции: упала любая — не применяется ни одна, и новый образ не стартует.
- Карточка `src/app/contacts/[id]/page.tsx` — серверный компонент в режиме просмотра: заголовок с `ContactCardActions` (окно `EditContactDialog` и `DeleteContactButton` с `AlertDialog`), строка «Добавлен … · изменён …», поля списком `dl`, общий с ним скелетон загрузки.
- Окна контакта построены на `ContactFormDialog`: окно держит `useTransition`, форма `ContactForm` получает `isPending` / `startTransition` и колбэки `onSaved` / `onCancel`; `noValidate`, ошибки у полей, Ctrl+Enter сохраняет, `disablePointerDismissal`, фокус при открытии ставится вручную.
- Серверные действия `src/app/contacts/actions.ts` проверяют ввод общей zod-схемой (`src/lib/contact-schema.ts`), возвращают `{ status: "saved" | "invalid" | "not-found" }` и после записи вызывают `revalidatePath`: ответ действия приносит свежие данные страницы, и карточка перерисовывается без перезагрузки.
- `next.config.ts`: `cacheComponents: true`. Данные из базы читаются внутри `Suspense`; текущее время в серверном компоненте можно брать только после обращения к динамическим данным, иначе сборка падает с ошибкой prerender. Перед кодом — читать гайды в `node_modules/next/dist/docs/` (правило `AGENTS.md`).
- UI: shadcn/ui в стиле `base-nova` поверх `@base-ui/react`; есть `alert-dialog`, `button`, `dialog`, `field`, `input`, `textarea`, `tooltip` и др. Иконки — `lucide-react`.
- `src/lib/dates.ts` — `APP_TIME_ZONE = "Europe/Moscow"`; `src/lib/format.ts` — `formatLongDate(date: Date)` даёт «24 октября 2026» в московском поясе.
- Тестовые заметки из `pnpm db:seed` — абзацы «ДД.ММ.ГГГГ — текст», разделённые пустой строкой. На проде, вероятно, такие же данные плюс реальные контакты.
- Репозиторий публичный: в миграциях и коде не должно быть данных конкретных контактов, только общие правила.

## Goals / Non-Goals

**Goals:**

- История мести — отдельная таблица, а не разбор текста заметок при каждом показе.
- Одна точка правды для «сегодня», одинаковая на сервере и в браузере.
- Разовый перенос из заметок в существующем конвейере миграций, без новых шагов выкатки.
- Без новых npm-библиотек и новых компонентов shadcn.
- Модель данных сразу годится для будущего «Пора мстить»: последняя месть считается по этой же таблице.

**Non-Goals:**

- Частота припоминаний, блок «Пора мстить», быстрые кнопки на главной — остаются в `new-features-and-keep-in-touch`.
- Показ последней мести в общем списке контактов, фильтры и сортировка по ней.
- Переименование кода под надписи интерфейса: в коде нейтральные английские имена (`interactions`, `occurred_on`, `summary`).
- Постраничная загрузка истории: записей у одного человека — десятки, грузим все.
- Настройка часового пояса: пользователь один, пояс зашит константой.

## Decisions

### 1. Модель данных

```
contacts                     interactions
  id  integer PK  ◄──────────  contact_id   integer NOT NULL → contacts.id ON DELETE CASCADE
  …   (без изменений)          id           integer PK (identity)
                               occurred_on  date NOT NULL
                               summary      text NOT NULL
                               created_at   timestamptz NOT NULL DEFAULT now()

index interactions (contact_id, occurred_on DESC, id DESC)
```

- **`occurred_on` — тип `date`**, в Drizzle `date(..., { mode: "string" })`: значение приходит строкой `"2026-10-24"` и нигде не превращается в `Date`, поэтому не съезжает на день из-за часовых поясов.
- **`summary` хранит итоговый текст**, включая «Отомстил» по умолчанию: подстановка делается при сохранении, а не при показе. В базе ровно то, что видно на экране.
- **Последняя запись не хранится в `contacts`**, а берётся первой из списка записей (`occurred_on desc, id desc`). Альтернатива — колонка `last_interaction_on` в `contacts` — отклонена: её надо пересчитывать при каждом добавлении, изменении и удалении записи.
- **`ON DELETE CASCADE`** — история удаляется вместе с контактом без изменений в `deleteContact`.
- Действия с записями не трогают `contacts.updated_at` (спека «Записи не меняют дату „изменён“»).
- **`updated_at` у `interactions` нет:** время правки записи нигде не показывается. Изменённая запись сохраняет `id`, поэтому среди записей с одной датой остаётся на прежнем месте («добавленная позже» — по `id`).
- Индекс покрывает единственный запрос — записи одного контакта в порядке показа — и пригодится будущему «Пора мстить» (`max(occurred_on)` по контакту).

### 2. «Сегодня» и часовой пояс

В `src/lib/dates.ts` к `APP_TIME_ZONE` добавляется `todayIsoDate()` — дата `"YYYY-MM-DD"` в этом поясе через `Intl.DateTimeFormat` с `timeZone` (собирается из `formatToParts`). Функция работает и на сервере, и в браузере, поэтому:

- дата по умолчанию в форме «Отомстил» — московское сегодня, даже если в браузере другой пояс;
- сервер проверяет «не позже сегодня» той же функцией;
- у поля даты `max` = сегодня, чтобы календарь браузера не предлагал будущие дни (окончательная проверка — схемой, форма с `noValidate`).

Альтернатива — пояс браузера через cookie — отклонена: лишняя сложность для одного пользователя.

### 3. Форматы дат

- `formatLongDate` учится принимать, кроме `Date`, строку `date`: «2026-10-24» → «24 октября 2026», без перевода через `Date` (месяц — из массива родительных падежей или через `Intl` с полуднем UTC; главное, чтобы день не съезжал). Нужна для строки «мстили …».
- `formatShortDate("2026-10-24")` → «24.10.2026» — собирается из частей строки, без `Date`. Нужна для записей и подтверждения удаления.

### 4. Проверка ввода

Новый `src/lib/interaction-schema.ts` по образцу `contact-schema.ts`:

- `occurredOn` — строка `YYYY-MM-DD`, реальная дата (не 2026-02-31), не позже `todayIsoDate()`; пустая → «Укажите дату», будущая → «Дата не может быть позже сегодняшней»;
- `summary` — `trim`, до 2000 символов («Слишком длинно: не больше 2000 символов»), пустая после `trim` → `DEFAULT_INTERACTION_SUMMARY` («Отомстил»);
- свой `toFieldErrors`.

Одна схема для добавления и изменения, общая для формы (мгновенные ошибки) и сервера (источник правды). «Сегодня» схема вычисляет при каждой проверке, а не при загрузке модуля: сервер живёт дольше суток.

### 5. Запросы и серверные действия

- `src/lib/interactions.ts` (`server-only`): `listInteractions(contactId)` — `id`, `occurredOn`, `summary` в порядке `occurred_on desc, id desc`.
- `src/app/contacts/interaction-actions.ts` (`"use server"`), результаты в стиле `actions.ts`:
  - `addInteraction(contactId, input)` → `saved | invalid | not-found`. Вставка через `insert … select … from contacts where id = …`: контакта нет — вставлено 0 строк → `not-found` (клиент показывает «Этот контакт не найден. Возможно, его удалили.»). Альтернатива — ловить ошибку внешнего ключа — отклонена: код ошибки приходит завёрнутым драйвером и ORM.
  - `updateInteraction(interactionId, input)` → `saved | invalid | not-found`; `contact_id` берётся из `returning`.
  - `deleteInteraction(interactionId)` → `deleted | not-found`; `contact_id` из `returning`.
  - После записи — `revalidatePath("/contacts/<contactId>")`. Главную не перепроверяем: на ней история не показывается.
  - Ids проверяются тем же способом, что `parseContactId` (для записи — общий разборщик положительного `integer`).
- `not-found` у изменения и удаления: сервер не знает, к какой карточке относилась исчезнувшая запись, поэтому клиент показывает `toast.error("Эта запись не найдена. Возможно, её удалили.")` и вызывает `router.refresh()`.

### 6. Карточка

Страница грузит контакт и его записи параллельно (`Promise.all` из `getContact` и `listInteractions` после разбора id). Строка «мстили …» рисуется на сервере из первой записи. Интерактивные части — клиентские компоненты:

```
ContactPage (server)
├─ BackLink «Весь список»                                     (есть)
├─ header: avatar, h1 name, ContactCardActions                (есть)
│    └─ DeleteContactButton                                   (меняется текст подтверждения)
├─ «мстили 24 октября 2026» / «Пока не мстили»                (новое, над «Добавлен …»)
├─ «Добавлен … · изменён …»                                   (есть)
└─ dl: Откуда знакомы, Телефон, Почта                         (есть)
       Последняя месть → InteractionSection (client)          (новое)
       │    ├─ последняя запись «ДД.ММ.ГГГГ Текст» / «Пока не мстили»
       │    ├─ «Вся история» → InteractionHistoryDialog: list | add | edit | confirm-delete
       │    └─ «Отомстил»   → InteractionDialog (Dialog + InteractionForm, add)
       Заметки                                                (есть)
```

- **`InteractionSection`** получает весь список записей (сериализуемые `{ id, occurredOn, summary }`) и `contactId`. Текст записи — `whitespace-pre-wrap`: перенесённые из заметок записи бывают многострочными. Расположение ссылки и кнопки — как в макете (на компьютере «Вся история» перед «Отомстил», на телефоне «Отомстил» первой строкой).
- **`InteractionForm`** — поля «Дата» (`Input type="date"`, по умолчанию `todayIsoDate()`) и «Как отомстил» (`Textarea`, серая подсказка «Отомстил»), кнопки «Сохранить» / «Отмена». Устроена как `ContactForm`: хозяин держит transition, форма получает `isPending` / `startTransition`, `onSaved` / `onCancel`; `noValidate`, ошибки у полей, фокус на первое неверное поле, Ctrl+Enter сохраняет. Режим `add` вызывает `addInteraction`, `edit` (поля заполнены) — `updateInteraction`. Ошибка сети — `toast.error` с тем же текстом, что у контакта, форма остаётся с введёнными данными.
- **`InteractionDialog`** — окно «Отомстил» из раздела: `Dialog` + `InteractionForm mode="add"`, оформление как у `ContactFormDialog` (заголовок, крестик, `disablePointerDismissal`, не закрывается во время сохранения, фокус при открытии — на поле «Как отомстил»). Закрытое окно размонтирует форму, поэтому каждое открытие начинается с сегодняшней даты и пустого текста.
- **`InteractionHistoryDialog`** — окно «История мести». Вид хранится в состоянии: `list` → «Отомстил» даёт `add`, карандаш — `edit` с записью, корзина — `confirm-delete` с записью; «Сохранить», «Удалить» и «Отмена» возвращают к `list`. Стрелка «Назад к истории» слева от заголовка — только в `add` и `edit`; в `confirm-delete` её нет, как в макете. Окон поверх окна нет: меняется только содержимое одного `Dialog`. Крестик и Esc закрывают окно целиком (во время запроса — нет). В `list` кнопка «Отомстил» стоит под заголовком (на телефоне — во всю ширину), у записи на телефоне текст под датой, иконки справа от даты. Пустой список — «Пока не мстили» и кнопка «Отомстил». Подтверждение показывает саму запись, текст «Запись от ДД.ММ.ГГГГ удалится насовсем.», кнопки «Отмена» (на ней фокус) и «Удалить» — на компьютере в ряд справа, на телефоне друг под другом; отдельный `AlertDialog` не нужен. При смене вида фокус переходит на заголовок нового вида (`tabIndex={-1}`), чтобы экранный диктор его объявил. Длинный список прокручивается внутри окна.
- **Иконки** — у записи `PencilIcon` («Изменить запись») и `Trash2Icon` («Удалить запись»), в форме окна истории `ArrowLeftIcon` («Назад к истории»); подсказки — shadcn `tooltip`, у кнопок `aria-label` (с датой записи, например «Изменить запись от 24.10.2026», чтобы диктор различал записи). На телефоне иконки-кнопки 44×44, на компьютере 36×36 — как у иконок заголовка.
- **`DeleteContactButton`** — меняется только текст: «Контакт «…», заметки и история мести удалятся насовсем. Вернуть их будет нельзя.» Записи удаляет `ON DELETE CASCADE`, `deleteContact` не меняется.
- **Скелетон** карточки дополняется строкой «мстили …» в заголовке и строкой «Последней мести» в списке полей, чтобы страница не прыгала.

Почему окно истории переключает виды, а не открывает окна поверх: решение владельца по макету (см. спеку «Без окон поверх окна истории»). Альтернатива — `AlertDialog` поверх `Dialog` — отклонена.

### 7. Перенос из заметок — SQL-миграция с PL/pgSQL

Две миграции:

1. `0001_create_interactions` — `pnpm db:generate --name=create_interactions` из схемы: таблица, внешний ключ, индекс.
2. `0002_copy_interactions_from_notes` — пишется руками (`pnpm drizzle-kit generate --custom --name=copy_interactions_from_notes`), один блок `DO $$ … $$`:
   - `today := (now() at time zone 'Europe/Moscow')::date`;
   - для каждого контакта с непустыми `notes` — разбить на строки (`\r?\n`); строка, совпавшая с `^\s*(\d{1,2})\.(\d{1,2})\.(\d{4})\s*[—–:-]?\s*(.*)$`, начинает запись, если `make_date(...)` даёт реальную дату (ошибку ловит `BEGIN … EXCEPTION`) и она не позже `today`; иначе строка — обычный текст;
   - строки без даты после датированной добавляются к её тексту; итоговый текст `btrim`, пустой → «Отомстил»;
   - текст до первой датированной строки делится на абзацы по пустым строкам; абзацы, где `lower(p collate "ru-RU-x-icu")` содержит одно из слов спеки, склеиваются через пустую строку в одну запись с датой `(updated_at at time zone 'Europe/Moscow')::date`;
   - записи вставляются в порядке строк заметок, поэтому при одинаковой дате «добавленной позже» считается та, что ниже в заметках;
   - `contacts` миграция не изменяет.

Почему SQL, а не TS-скрипт: миграция идёт в существующем шаге выкатки, ровно один раз (её учитывает журнал Drizzle) и в той же транзакции, что и создание таблицы. TS-скрипту понадобился бы новый шаг в `deploy.sh` и свой признак «уже выполнено».

Почему `collate "ru-RU-x-icu"` для `lower`: регистр кириллицы в `lower()` зависит от локали базы, а ICU-коллация уже используется приложением для сортировки списка и даёт правильный результат независимо от локали.

### 8. Тестовые данные

`scripts/seed-data.ts` вместе с каждой заметкой «ДД.ММ.ГГГГ — текст» создаёт такую же запись о мести (`generateContacts` возвращает контакт вместе с его записями). `scripts/seed.ts` вставляет контакты пачками с `returning({ id })`, затем их записи — в той же транзакции. На свежей базе перенос из заметок отрабатывает на пустой таблице, поэтому без этого шага истории в тестовых данных не было бы. Непустую базу seed по-прежнему не трогает.

### 9. Компоненты shadcn

Новых не нужно. Поле даты — `Input type="date"`: календарь shadcn тянет `react-day-picker`, это новая зависимость.

## Risks / Trade-offs

- [Правило «дата в начале строки = запись» переносит и посторонние сведения, например «15.10.2026 — Дети: …»] → Так решил владелец; заметки не меняются, лишнюю запись можно изменить или удалить в окне истории.
- [Слова-признаки для текста без даты пропустят нужное или поймают лишнее] → Перенос только копирует; список слов зафиксирован в спеке; недостающую запись владелец добавит кнопкой «Отомстил».
- [Ошибка в PL/pgSQL роняет выкатку] → Миграция в одной транзакции со схемой: упала — база не меняется, работает старая версия. Перед PR прогнать миграции на локальной базе с 1000 тестовыми контактами и сверить счётчики (число датированных строк в заметках = число записей с этих строк).
- [Пользователь в другом часовом поясе увидит «сегодня» по Москве] → Пользователь один и в Москве; пояс — одна константа.
- [Смена видов внутри окна истории: можно потеряться, где находишься] → У каждого вида свой заголовок, фокус переходит на него; «Отмена» всегда возвращает к списку, в формах — ещё и стрелка «назад».
- [Порядок с `new-features-and-keep-in-touch`: она сокращена до частоты и «Пора мстить» и опирается на таблицу `interactions` и модули дат отсюда] → Вливать её строго после этой; её миграция идёт следующим номером после `0002`.

## Migration Plan

1. PR в `main` → CI собирает образ → `deploy.sh` применяет `0001` и `0002` в одной транзакции → стартует новое приложение → smoke `/health`.
2. Проверка после выкатки: открыть контакт с датированными заметками — под именем «мстили …», в «Последняя месть» последняя запись, в «Вся история» все датированные абзацы; заметки и дата «изменён» прежние.
3. Откат — только вручную, по README. Миграции только добавляют (новая таблица), поэтому предыдущий образ работает с новой базой и просто не видит историю. Повторная выкатка новой версии перенос не повторит — миграция уже записана в журнале.
4. Если перенос дал не тот результат — записи удаляются в интерфейсе или отдельной миграцией по согласованию; автоматического отката нет.
