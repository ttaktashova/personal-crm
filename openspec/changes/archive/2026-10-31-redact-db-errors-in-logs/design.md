# Design

## Context

Мотивация — в `proposal.md` (Why), требования — в `specs/error-logging/spec.md`.

Как устроено сейчас:

- `src/db/index.ts` создаёт клиент `postgres` (postgres.js 3.4.9) и экспортирует `db = drizzle(client, { schema })` (drizzle-orm 0.45.4). `db` импортируют напрямую:
  - серверные действия: `src/app/contacts/actions.ts` (`createContact`, `updateContact`, `stopReminders`, `deleteContact`) и `src/app/contacts/interaction-actions.ts` (`insertInteraction` для `addInteraction` и `markContacted`, `updateInteraction`, `deleteInteraction`);
  - чтение для страниц: `src/lib/contacts.ts` (`listContactsPage`, `findContactPage`, `getContact`), `src/lib/interactions.ts` (`listInteractions`), `src/lib/keep-in-touch.ts` (`listDueContacts`);
  - `src/app/health/route.ts` — `select 1`, ошибку пишет сам: `console.error("Health check failed:", error)`.
- Ошибку любого запроса Drizzle заворачивает в `DrizzleQueryError` (`drizzle-orm/errors.js`, бросается из `PgPreparedQuery.queryWithCache`). Сообщение — `Failed query: <SQL>\nparams: <значения через запятую>`. У ошибки есть свои поля `query` и `params`, а в `cause` лежит исходная ошибка. Это касается и ошибок соединения: при остановленной базе в сообщении всё равно все значения. Отключить это настройкой нельзя, у `logger` Drizzle нет обработчика ошибок.
- Исходная ошибка postgres.js (`PostgresError`) показывает при выводе поля `message`, `detail`, `where`, `hint`, `code`, `table_name`, `column_name`, `constraint_name` и др. Значения бывают в трёх из них: `detail` («Failing row contains (…)», «Key (…)=(…)»), `where` («unnamed portal parameter $1 = '…'») и `message` («invalid input syntax for type date: "…"»). Поля `query` и `parameters` postgres.js скрывает, пока не включён `debug`.
- Next.js пишет в stdout/stderr процесса необработанные ошибки серверных действий, серверных компонентов и обработчиков маршрутов: сообщение, стек, собственные поля и `cause`. На сервере это `docker logs` контейнера `app`. В браузер в рабочей сборке уходит только общее сообщение и `digest`, так что сам браузер не проблема.
- Формы ловят любую ошибку действия и показывают сообщение (`contact-form.tsx`, `interaction-form.tsx`, `delete-contact-button.tsx`, `due-contacts-list.tsx`, `interaction-history-dialog.tsx`), сбой страницы показывает `src/app/error.tsx`. Что пришло в ошибке, им не важно.
- `scripts/migrate.mjs` — простой JS: в образе нет TypeScript и нет `src/`. Dockerfile копирует в `/app/migrate` только этот файл, `drizzle/` и пакеты `drizzle-orm` и `postgres`. Ошибка `migrate()` сейчас не ловится, и Node печатает её целиком. `deploy.sh` выводит это в лог GitHub Actions, а при красном smoke добавляет туда ещё `compose logs --tail 50 app`. Репозиторий публичный.
- Автотестов в проекте нет: проверка — `pnpm typecheck`, `pnpm lint`, `pnpm build` и руками.

## Goals / Non-Goals

**Goals:**

- Одно место, где ошибка базы превращается в безопасную. Запрос мимо него написать нельзя: `db` наружу не экспортируется.
- Запись в журнале остаётся полезной: какой запрос, код ошибки, имена из схемы.
- Без новых библиотек, без изменений для пользователя, без изменений в базе и выкатке.

**Non-Goals:**

- **Журнал самого Postgres** (контейнер `db`). По умолчанию Postgres не пишет значения параметров при ошибке (`log_parameter_max_length_on_error = 0`), а текст запроса пишет с `$1`, `$2` вместо значений. Строку целиком он пишет только в `DETAIL` при нарушении NOT NULL, CHECK или UNIQUE. В нашей схеме нет CHECK и UNIQUE, а NOT NULL и тип значений проверяет сервер ещё до запроса. Настройки Postgres не меняем.
- Журнал доступа nginx со словами поиска в адресе и вывод аргументов в терминал при `pnpm dev`: владелец решил их не брать (proposal, пункты 5 и 6).
- Ошибки не от базы. Проверка ввода (zod) ничего не бросает, а собственные ошибки кода данных не несут.
- Внешние сервисы сбора ошибок: их нет и не добавляем.

## Decisions

### 1. Все запросы — через `runQuery(label, run)`, `db` не экспортируется

В `src/db/index.ts` остаётся модульная константа `db`, а наружу выходит одна функция:

```ts
export async function runQuery<T>(label: string, run: (db: Database) => PromiseLike<T>): Promise<T>
```

Она вызывает `run(db)`. Если вызов упал, она бросает `DatabaseError` (решение 2) вместо исходной ошибки. `label` — имя функции, в которой стоит запрос: `createContact`, `listContactsPage`, `insertInteraction`, `healthCheck` и т. д. Если в функции несколько запросов подряд (`listContactsPage`, `findContactPage`), они стоят в одном `runQuery` с `async`-колбэком. Построители запросов Drizzle — thenable, поэтому `run` может вернуть их без `await`.

Почему метка, а не только стек: на сервере код Next.js сжат, и в стеке вместо имён функций — номера строк в чанках. Метка читается всегда.

Отклонённые варианты:

- **`safeQuery(db.insert(…))` при открытом `db`.** Ту же обёртку легко забыть в новом запросе, и ничто не подскажет.
- **Обернуть целиком каждое действие и функцию чтения.** Тогда очищались бы и ошибки не от базы. Стало бы труднее разбираться с собственными багами, а данных они и так не несут.
- **Подменить `console.error` в `instrumentation.ts`.** Это поймало бы всё, включая будущий код, но это скрытый глобальный трюк. Он завязан на то, как именно Next печатает ошибки, и мешал бы собственной отладке.
- **Proxy вокруг `db` или правка `DrizzleQueryError`.** Цепочки построителей и правка библиотеки — слишком хрупко ради 13 мест вызова.

### 2. `DatabaseError` несёт только коды и имена из схемы

Новый `src/db/database-error.ts`:

- `name = "DatabaseError"`. Сообщение: `Database query failed: <label> (code <code>[, table <t>][, column <c>][, constraint <k>])`, например `Database query failed: createContact (code ECONNREFUSED)`. Если кода нет — `code unknown`.
- Поля `label`, `code`, `table`, `column`, `constraint` лежат в самой ошибке, Next печатает их вместе с ней.
- Значения берутся из ошибки и её цепочки `cause` (Drizzle → postgres.js → сетевая ошибка Node). Используется первое найденное строковое `code`, `table_name`, `column_name`, `constraint_name`. Пропускается только то, что похоже на код или имя: код — `^[0-9A-Z_]{1,64}$` (`23514`, `42P01`, `ECONNREFUSED`, `CONNECT_TIMEOUT`), имя — `^[a-z_][a-z0-9_]{0,62}$`. Всё остальное отбрасывается. Так в запись не попадёт значение, даже если библиотека однажды положит его в эти поля.
- Не копируются `message`, `detail`, `where`, `hint`, `query`, `params`, стек исходной ошибки. `cause` не ставится: Node печатает `[cause]` целиком. Стек — собственный, от места создания в `runQuery`.

Почему не оставить `message` Postgres: в нём бывают значения (см. Context). Код вместе с меткой и именами из схемы почти всегда говорит то же самое: `42P01` — нет таблицы, `23503` + `constraint` — нарушен внешний ключ, `ECONNREFUSED` — база не отвечает.

### 3. Миграции: своя короткая копия правила в `scripts/migrate.mjs`

`migrate()` оборачивается в `try/catch`. При ошибке печатается `Migrations failed (code …[, table …][, column …][, constraint …])` по тем же правилам, что в решении 2, и ставится `process.exitCode = 1`. `finally` с `client.end()` остаётся. `deploy.sh` не меняется: `run --rm migrate || fail "migrations failed…"` по-прежнему останавливает выкатку до запуска нового образа.

Правило отбора полей (около 15 строк) повторено в `migrate.mjs`, а не вынесено в общий модуль. Файл работает в образе без TypeScript и без `src/`, и общий `.mjs` пришлось бы отдельно копировать в Dockerfile ради 15 строк. В обоих файлах — комментарий со ссылкой на второй.

### 4. `/health` — тоже через `runQuery`

`runQuery("healthCheck", (db) => db.execute(sql\`select 1\`))`. `console.error("Health check failed:", error)` остаётся: в нём теперь `DatabaseError`. Ответы прежние: 200 `{"status":"ok"}` или 503 `{"status":"error"}`.

### 5. Что видит владелец — без изменений

`DatabaseError` бросается туда же, куда раньше `DrizzleQueryError`. Формы показывают те же сообщения, страницы — тот же `error.tsx`. Проверки «контакт не найден» опираются на пустой результат запроса, а не на ошибку, поэтому не меняются.

### 6. Как проверяем

- Сбои проверяем на рабочей сборке (`pnpm build`, `pnpm start`), как на сервере. `pnpm dev` дополнительно печатает в терминал каждый вызов действия с аргументами (это настройка Next для разработки, `logging.serverFunctions`) и запутал бы проверку.
- «База недоступна» — `docker compose stop postgres` при запущенном приложении, затем `docker compose start postgres`.
- «База отклонила строку» — временная база `crm_logs_check` рядом с основной в локальном контейнере (`createdb` / `dropdb`) с временным ограничением `contacts_logs_check check (notes = '')`. Контакт с заметкой база отклонит и перечислит в пояснении все значения строки. В самом ограничении проверяемых значений нет, поэтому если они найдутся в журнале, значит, пришли из строки. Приложение запускается с `POSTGRES_DB=crm_logs_check`: переменная окружения главнее `.env`, а сам `.env` не читаем.
- Сбой миграции — та же временная база с контактом «Пётр Тестов» с заметкой. `migrate.mjs` запускается из временной папки с копией `drizzle/` и лишней миграцией. Она добавляет то же ограничение с `not valid` и обновляет строки `contacts`, поэтому падает на этом контакте, и в пояснении базы оказывается вся строка. Строку подключения собирает `getDatabaseUrl()` после `loadEnvConfig`, как в `scripts/seed.ts`, и на экран её не выводим.
- Сначала воспроизводим утечку на нынешнем коде: так проверка доказывает, что ловит именно то, что нужно.

## Risks / Trade-offs

- [Новый запрос напишут мимо `runQuery`] → `db` не экспортируется, обойти можно только новым клиентом. В `src/db/index.ts` комментарий, зачем это сделано.
- [Без `message` Postgres причину иногда понять труднее] → метка, код и имена из схемы почти всегда достаточны. Если нет — ошибку воспроизводим локально на тестовых данных, где подробности смотреть можно.
- [Метка разойдётся с именем функции после переименования] → метки — простые строки рядом с функцией, проверяются глазами на ревью. Ошибка в метке не раскрывает данных.
- [Правило отбора полей продублировано в `migrate.mjs`] → 15 строк и взаимные комментарии. Если правило поменяется, правим оба места.
- [Next начнёт печатать ещё что-то, например аргументы действий в рабочей сборке] → сейчас такого нет (в рабочей сборке только ошибка). Проверка из решения 6 смотрит на весь вывод процесса, а не только на запись об ошибке.
- [Старые записи с данными в журнале нынешнего контейнера] → при выкатке `up -d` пересоздаёт контейнер `app`, и его журнал удаляется вместе с ним, если Docker хранит журналы по умолчанию (`json-file` или `local`). После выкатки владелец проверяет командой из tasks.md. Сами ничего не удаляем.

## Migration Plan

1. Обычная выкатка через PR и merge в main. Миграций базы нет, шаг миграций пройдёт без изменений.
2. После выкатки — smoke `/health` (зелёный), затем проверка журналов на сервере командами из tasks.md.
3. Откат — только вручную, по README: прежний образ работает с той же базой. Он снова будет писать значения в журнал при сбоях, но данные не портит.
