# Черный список

Личная CRM, но не телефонный справочник, а блокнот тех, кому хочется отомстить: кто это, откуда знакомы, телефон, почта и заметки о том, что натворил и чем всё закончилось. Чтобы никого не забыть и вовремя припомнить.

Идея и критерии успеха — в [`specs/01-продуктовая-идея.md`](specs/01-продуктовая-идея.md).

## Что нужно установить

- [Node.js](https://nodejs.org/) 24
- [pnpm](https://pnpm.io/)
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) — в нём работают база данных PostgreSQL и почтовая заглушка Mailpit

## Первый запуск

1. Скопируйте `.env.example` в `.env` и заполните значения:
   - имя пользователя, пароль и название базы (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`). Вместо них можно указать одну строку подключения `DATABASE_URL`;
   - `BETTER_AUTH_SECRET` — секрет, которым подписывается вход. Любая длинная случайная строка, например вывод `openssl rand -hex 32` в Git Bash. Поменяли — все входы заканчиваются, нужно войти заново;
   - `BETTER_AUTH_URL=http://localhost:3000` — адрес приложения: из него строится ссылка в письме, и вход держится только на этом адресе;
   - `SMTP_URL=smtp://127.0.0.1:1025` — куда отправлять письма. Этот адрес — почтовая заглушка Mailpit: письма не уходят в настоящие ящики, а видны на её странице;
   - `EMAIL_FROM=noreply@mail.crm.testblacklist.ru` — адрес отправителя писем;
   - `OWNER_EMAIL` — ваша почта: все контакты и группы, которые уже были в базе до появления входа, достаются пользователю с этой почтой, и тестовые контакты `pnpm db:seed` создаются у него же.
2. Запустите базу данных и почтовую заглушку:
   ```
   docker compose up -d
   ```
   Страница заглушки с письмами — http://127.0.0.1:8025
3. Установите зависимости:
   ```
   pnpm install
   ```
4. Создайте таблицы в базе:
   ```
   pnpm db:migrate
   ```
   Команде нужна строка `OWNER_EMAIL` в `.env`: без неё (или с неправильной почтой) она пишет `Migrations failed: OWNER_EMAIL is not set or is not an email` и ничего не меняет.
5. По желанию — заполните список владельца, пользователя с почтой из `OWNER_EMAIL`, 1000 тестовыми контактами вместе с историей мести: к каждой заметке с датой — такая же запись. Примерно у четверти контактов задана частота «Как часто припоминать», так что на главной сразу есть блок «Пора мстить», а примерно 60 % людей разложены по группам владельца, по одной-три группы на человека. Сработает, только если у владельца ещё нет контактов (иначе команда пишет `Seed skipped` и ничего не меняет); данные других пользователей не трогает. Увидеть контакты — войти под почтой из `OWNER_EMAIL`:
   ```
   pnpm db:seed
   ```
6. Запустите приложение:
   ```
   pnpm dev
   ```
   и откройте http://localhost:3000

## Как войти на своём компьютере

Без входа приложение открывает страницу входа. Паролей нет: вход — по ссылке из письма.

1. Откройте приложение по адресу из строки `BETTER_AUTH_URL` в `.env` — http://localhost:3000. Вход держится только на этом адресе: если открыть http://127.0.0.1:3000, приложение снова попросит войти.
2. Введите почту и нажмите «Получить ссылку». Подойдёт любая, даже выдуманная (`friend@example.com`): письма на компьютере никуда не уходят.
3. Откройте страницу почтовой заглушки Mailpit — http://127.0.0.1:8025, письмо «Вход в Черный список» и в нём кнопку «Войти». Ссылка работает 15 минут и один раз.

Под своей почтой из `OWNER_EMAIL` вы видите все контакты, которые были в базе до появления входа. Другой адрес — другой пользователь: свой пустой список и свои группы. Чтобы посмотреть приложение глазами двух людей сразу, войдите во втором браузере (или в окне инкогнито) под другой почтой.

## Обычный запуск

Если всё уже настроено:

```
docker compose up -d
pnpm build
pnpm start
```

Приложение откроется по адресу http://localhost:3000. Остановить — `Ctrl+C` в окне, где оно запущено. Остановить базу — `docker compose stop` (данные сохраняются).

Приложение доступно только с этого компьютера: для других устройств в сети оно не открыто.

## Проверки перед влитием (CI)

В `main` изменения попадают только через pull request (PR), напрямую push в `main` GitHub не примет. На каждый PR GitHub сам запускает проверки (`.github/workflows/ci.yml`), они видны внизу страницы PR:

- **Checks** — линтер (`pnpm lint`), оформление кода (`pnpm format:check`), типы (`pnpm typecheck`) и автотесты Vitest (`pnpm test`) на настоящем Postgres
- **E2E** — сквозной тест главного сценария в браузере (`pnpm test:e2e`). Если он упал, на странице запуска во вкладке **Actions** внизу появляется архив `playwright-report` со снимками экрана и записью шагов
- **Image** — сборка образа приложения, такого же, как при выкатке (на сервер он не попадает)

PR вливается, только когда все три проверки зелёные. Если включено автовлитие (`gh pr merge --auto --squash` или кнопка **Enable auto-merge** на странице PR), PR вольётся сам сразу после зелёных проверок. Красная проверка — PR ждёт, пока её не починят: новый push в ту же ветку запускает проверки заново.

## Выкатка на сервер

Новая версия идёт в два шага:

1. **На тест-стенд — сама.** После того как PR влит в `main`, GitHub собирает образ и выкатывает его на тест-стенд. Прод при этом не меняется.
2. **На прод — только когда вы нажмёте кнопку** (workflow **Deploy prod**). На прод едет тот же образ, что на стенде, и только версия, которая удачно выкатилась на стенд. Исключение — откат.

### Выкатка на тест-стенд (сама, после влития в `main`)

Ход выкатки — на GitHub во вкладке **Actions** → слева **Deploy staging**: в запуске два шага — **Build image** и **Deploy staging**. Зелёная галочка — выкатилось, красный крестик — выкатка упала.

1. GitHub собирает образ приложения и кладёт его в GitHub Container Registry (GHCR) с номером коммита в имени.
2. Копирует на сервер всю папку `deploy/` (новый скрипт в ней уезжает сам) в папку стенда и запускает `deploy/deploy.sh staging`.
3. Скрипт скачивает образ, разовым контейнером из нового образа применяет миграции базы и только потом запускает новую версию. Упали миграции — новая версия не запускается, работает старая. В логе тогда будет строка `Migrations failed (code …)`: код ошибки и, если база их назвала, имена таблицы, поля и ограничения. Данных контактов в ней нет.
4. Скрипт проверяет, что `/health` отвечает 200. Не ответил — выкатка считается упавшей. Сам он ничего не откатывает.

История выкаток стенда — на главной странице репозитория справа, **Deployments → staging**. По ней **Deploy prod** проверяет, какие версии прошли стенд.

### Выкатить на прод

1. Убедитесь, что новая версия на стенде: **Actions → Deploy staging** — у нужного влития зелёная галочка. Посмотрите её руками на https://test-app.testblacklist.ru.
2. На GitHub: вкладка **Actions** → слева **Deploy prod** → справа кнопка **Run workflow**.
3. В открывшемся окошке:
   - **Use workflow from** — оставьте `Branch: main`. С другой ветки выкатка сразу остановится: на прод уезжают только скрипты, прошедшие PR;
   - **Version (commit SHA)** — оставьте пустым: выкатится версия последней удачной выкатки на тест-стенд;
   - **Roll back…** — галочку не ставьте.
4. Нажмите зелёную **Run workflow**. Через несколько секунд в списке появится запуск — откройте его.
5. Зелёная галочка — выкатилось. Внизу страницы запуска, под схемой шагов, — итог:
   - `Version` — какая версия выкатилась (номер коммита, ссылка на него);
   - `Chosen` — как выбрана: `the last successful staging deploy` (последняя со стенда), `given by hand` (вписана руками) или `rollback` (откат);
   - `Before this run` — какая версия была на проде до этого;
   - `Old images in GHCR` — чистка старых образов (ниже).

Что делает **Deploy prod**:

1. Выбирает версию и проверяет, что она удачно выкатывалась на тест-стенд. Не выкатывалась — останавливается, на проде ничего не меняется.
2. Записывает выкатку в историю: на главной странице репозитория справа, **Deployments → prod**, — та версия, что сейчас на проде.
3. Копирует на сервер папку `deploy/` и запускает `deploy/deploy.sh prod`. Скрипт на сервере:
   - ставит или обновляет таймер ежедневного бэкапа (раздел «Бэкапы»);
   - скачивает образ (если его ещё нет на сервере);
   - снимает бэкап базы — копию всех данных на момент перед выкаткой. Бэкап не получился — выкатка падает: миграции не применяются, новая версия не запускается, работает старая;
   - применяет миграции разовым контейнером, запускает новую версию, проверяет `/health` — так же, как на стенде;
   - удаляет старые образы на сервере.
4. Удаляет старые образы из GHCR.

**Как проверить после выкатки:**

1. В итоге запуска `Prod: deployed` и нужная версия в `Version`.
2. https://app.testblacklist.ru открывается, вход по ссылке из письма работает, контакты на месте.
3. Справа на главной странице репозитория, **Deployments → prod**, — та же версия.

**Конкретную версию** (запасной путь) — в поле **Version (commit SHA)** впишите номер коммита: первые 7 знаков из списка коммитов `main` на GitHub или полный. Выкатится, только если эта версия хоть раз удачно выкатывалась на тест-стенд; иначе запуск остановится с ошибкой `version … has never deployed to staging successfully`, на проде ничего не изменится.

### Откатить прод

Только вручную, запускаете вы:

1. **Actions → Deploy prod → Run workflow**.
2. Поставьте галочку **Roll back to the prod version before the current one**. Поле **Version** при этом не смотрится, оставьте как есть.
3. **Run workflow**.

Прод вернётся на версию, которая работала до текущей: её помнит сервер (файл `/opt/personal-crm/previous-image`), образ её лежит на сервере, тест-стенд при откате не проверяется. В итоге запуска `Chosen: rollback…` и вернувшаяся версия.

- Откат меняет только версию приложения: изменения структуры базы, которые успела применить новая версия, остаются. Перед откатом скрипт тоже снимает бэкап базы, как при обычной выкатке.
- Сервер помнит две версии: текущую и предыдущую. Второй откат подряд вернёт ту версию, с которой вы откатились. Вернуться на две версии назад — **Deploy prod** с номером нужной версии в поле **Version**.
- Если GitHub недоступен — откат прямо на сервере, в своём терминале:
  ```
  ssh crm 'bash /opt/personal-crm/deploy/deploy.sh prod "$(cat /opt/personal-crm/previous-image)"'
  ```
  Такой откат в историю **Deployments** на GitHub не попадает.

### Если выкатка упала

Красный крестик у запуска. Первая строка итога говорит, где:

- `NOT DEPLOYED: a step before the deploy failed, prod was not changed` — упало до сервера: неверный номер версии, версия не проходила стенд, откатывать некуда, запуск не из `main`. Причина — красным в логе шага **Choose the version** (или **Check the branch**). На проде ничего не менялось.
- `DEPLOY FAILED` — упало на сервере. Откройте шаг **Deploy on the server**: внизу строка `DEPLOY FAILED (prod): …` с причиной. Если упал бэкап или миграции — работает прежняя версия. Если новая версия не ответила на `/health` (`did not pass the smoke check`) — она запущена, но не работает; сам скрипт ничего не откатывает: решите, откатывать ли (раздел выше).
- `Prod: deployed`, но `Old images in GHCR: FAILED` — прод выкатился, не удалась только чистка GHCR. Скорее всего, у репозитория нет прав на пакет: на GitHub ваш профиль → **Packages → personal-crm → Package settings → Manage Actions access** — у репозитория `personal-crm` роль **Admin**.

Две выкатки на одно окружение, выкатка и восстановление базы, выкатка и бэкап одного окружения одновременно не идут. На GitHub следующая выкатка ждёт, пока закончится предыдущая. Если на сервере уже работает `deploy.sh`, `restore.sh` или ежедневный бэкап для этого окружения, выкатка сразу останавливается с сообщением `another deploy, restore or backup of prod is running on this server` (или `of staging`) и ничего не меняет. Перезапустите её: страница запуска → **Re-run jobs**. Стенд и прод друг друга не ждут.

Старые запуски workflow **Deploy** (до того, как прод стал выкатываться кнопкой) не перезапускайте: они выкатили бы прод старыми скриптами в обход проверки стенда.

### Чистка старых образов

После каждой удачной выкатки на прод:

- в GHCR остаются 10 последних сборок (одна сборка — одно влитие в `main`), старые удаляются;
- на сервере удаляются образы старше 2 недель, кроме текущей и предыдущей версии прода и текущей версии стенда — они остаются при любом возрасте, поэтому откат работает всегда.

Версию, которой уже нет ни на сервере, ни среди 10 последних сборок в GHCR, выкатить нельзя — только более новую.

### Логи

Логи — записи, которые приложение и база пишут о себе во время работы: запуск, ошибки базы (`Database query failed: createContact (code ECONNREFUSED)`), неотправленные письма (`Sign-in email failed (code EAUTH)`). Данных контактов, почт и ссылок для входа в них нет — только что сломалось и код ошибки.

Все контейнеры прода и стенда пишут логи в журнал сервера (journald), а не в свои файлы внутри Docker. Поэтому записи переживают выкатку и откат: контейнер приложения заменяется новым, а записи прежней версии остаются в журнале. Журнал хранится на диске и переживает перезагрузку сервера. Его размер ограничивает сама система — не больше 3,9 ГБ (10% диска), самые старые строки удаляются, диск не забивается. Настроено в `deploy/compose.yaml`, общие настройки Docker на сервере не менялись.

В каждой строке — время, имя контейнера и сама запись. Контейнеры: приложение `prod-app-1` и `staging-app-1`, база `prod-db-1` и `staging-db-1`, миграции — `prod-migrate-run-…` и `staging-migrate-run-…` (их вывод есть и в логе выкатки на GitHub). Имя `prod-app-1` одно у всех версий прода: записи всех версий идут подряд.

Читать журнал — через `sudo` (обычный пользователь сервера видит только свои записи). Команды для прода; для стенда — `staging-app-1`, для базы — `prod-db-1`:

- последние 100 строк:
  ```
  ssh crm sudo journalctl CONTAINER_NAME=prod-app-1 -n 100 --no-pager
  ```
- за последний час (или `--since -1d` — за сутки, `--since "2026-11-14 11:00"` — с момента по времени сервера, московскому):
  ```
  ssh crm sudo journalctl CONTAINER_NAME=prod-app-1 --since -1h --no-pager
  ```
- следить вживую — `-f` вместо `-n 100 --no-pager`, выход — Ctrl+C;
- только одной версии, например той, которую откатили (полный номер версии — в итоге запуска **Deploy prod**):
  ```
  ssh crm sudo journalctl CONTAINER_NAME=prod-app-1 IMAGE_NAME=ghcr.io/ttaktashova/personal-crm:<полный номер> --no-pager
  ```

`ssh crm docker logs prod-app-1` тоже работает, но показывает только текущий контейнер — записей прежних версий в нём нет.

Записи ежедневного бэкапа — в том же журнале, команда в разделе «Бэкапы».

### Сервер и окружения

Адрес сервера: `153.76.175.40`, войти — `ssh crm`. Приложение и база работают в Docker, у каждого окружения своя база в отдельном контейнере со своим хранилищем. Наружу приложение открыто только через nginx.

| | Прод | Тест-стенд |
|---|---|---|
| адрес | https://app.testblacklist.ru | https://test-app.testblacklist.ru, закрыт паролем |
| папка на сервере | `/opt/personal-crm` | `/opt/personal-crm/staging` |
| скрипты выкатки | `/opt/personal-crm/deploy` | `/opt/personal-crm/staging/deploy` |
| настройки | `/opt/personal-crm/.env` | `/opt/personal-crm/staging/.env` |
| проект Docker, контейнеры | `prod`: `prod-app-1`, `prod-db-1` | `staging`: `staging-app-1`, `staging-db-1` |
| порт приложения на сервере | 3000 | 3001 |
| лимит памяти | нет | приложение 512 МБ, база 256 МБ |
| выкатка | кнопкой, **Actions → Deploy prod** | сама после влития в `main`, **Actions → Deploy staging** |
| бэкапы | каждый день в 03:00 по Москве и перед каждой выкаткой | нет |

Настройки окружения лежат в его `.env` с правами 600, в git их нет. Какие строки там нужны — в `deploy/server.env.example`. Для прода:

- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` — база;
- `BETTER_AUTH_SECRET` — секрет входа: длинная случайная строка, `openssl rand -hex 32` на сервере. Поменяли — все входы заканчиваются;
- `BETTER_AUTH_URL=https://app.testblacklist.ru` — адрес приложения: на него ведут ссылки в письмах;
- `SMTP_URL=smtps://resend:<ключ API>@smtp.resend.com:465` — письма уходят через Resend;
- `EMAIL_FROM=noreply@mail.crm.testblacklist.ru` — адрес отправителя;
- `OWNER_EMAIL` — ваша почта: при первой выкатке со входом все контакты и группы, которые были в базе, достаются пользователю с этой почтой. Сверьте её по буквам.

Если какой-то строки нет или она пустая, выкатка останавливается в самом начале с сообщением `required variable OWNER_EMAIL is missing a value: set OWNER_EMAIL in .env` (с именем той строки, которой нет): ни бэкапа, ни миграций, работает прежняя версия. Посмотреть, какие строки есть, не показывая значений: `ssh crm "cut -d= -f1 /opt/personal-crm/.env"`.

**Письма через Resend.** Настоящие письма со ссылкой для входа сервер отправляет через сервис [Resend](https://resend.com). В нём подтверждён домен `mail.crm.testblacklist.ru`: записи DNS из вкладки **Domains → Records** добавлены в Timeweb, у домена статус «Verified». Ключ API с правом отправки — в строке `SMTP_URL`. Если письма перестали приходить, в логах приложения (`ssh crm sudo journalctl CONTAINER_NAME=prod-app-1 -n 100 --no-pager`, раздел «Логи») будет `Sign-in email failed (code …)`: `EAUTH` — неверный ключ, `ESOCKET` — Resend не ответил.

Проверить, что работает:

```
ssh crm curl -s http://127.0.0.1:3000/health
```

Ответ `{"status":"ok"}` — приложение работает и видит базу. `/health` открыт без входа.

После выкатки входа проверьте руками:

1. https://app.testblacklist.ru открывает страницу входа.
2. Ссылка для входа приходит на вашу почту из `OWNER_EMAIL` (письмо «Вход в Черный список» от «Черный список»). По ней — все прежние контакты, записи о мести, группы с теми же людьми и блок «Пора мстить».
3. Вход под другой почтой (например, второй вашей) — пустой список, «Пока некому мстить» и пять новых групп: «Бывшие», «Должники», «Коллеги», «Не любят котиков», «Родственники».

**Откат выкатки, в которой появился вход, — только вместе с базой и только в таком порядке.** Эта выкатка меняет данные: у контактов и групп появляется владелец, без него база их больше не пускает. Прежняя версия на новой базе не смогла бы добавлять контакты и показала бы всем все данные без входа. Поэтому:

1. Сначала база — восстановите бэкап, снятый перед этой выкаткой (в имени — `deploy` и версия, которая работала до неё), как описано в разделе «Восстановление базы из бэкапа»:
   ```
   bash /opt/personal-crm/deploy/restore.sh prod /opt/personal-crm/backups/<бэкап перед выкаткой>.dump
   ```
2. Потом приложение — версия, которая работала до входа: её номер — в имени того же бэкапа, после `deploy_`. На сервере, в своём терминале:
   ```
   bash /opt/personal-crm/deploy/deploy.sh prod ghcr.io/ttaktashova/personal-crm:<версия из имени бэкапа>
   ```
   Не через **Deploy prod**: та версия не проходила тест-стенд (его тогда ещё не было), и после входа выкатывались другие версии, так что галочка отката её уже не вернёт. Её образ хранится не вечно — раздел «Чистка старых образов».

Между шагами новая версия на старой базе только отвечает ошибками и ничего не показывает. Всё, что добавили после выкатки, пропадёт (останется в копии `before-restore`).

## Тест-стенд

https://test-app.testblacklist.ru — второе приложение на том же сервере, чтобы проверять новую версию на копии настоящих данных. После каждого влития в `main` новая версия сначала выкатывается сюда (тем же скриптом `deploy.sh staging`, только без бэкапа), а на прод тот же образ попадает, когда вы запустите **Deploy prod**. Ход выкатки — **Actions** → **Deploy staging**.

У стенда всё своё, с продом он ничего не делит: база, `.env`, секрет входа, ключ Resend, адрес. Что на стенде добавили или удалили, на прод не попадает.

**Пароль на весь стенд.** Браузер сначала спрашивает логин и пароль — без них ошибка 401. Это замок перед приложением, а не вход в него: за ним обычная страница входа по ссылке из письма. Пароль хранит nginx в файле `/etc/nginx/test-app.testblacklist.ru.htpasswd` (не сам пароль, а его хеш), в приложение он не передаётся. Задать или сменить — в своём терминале (не через Claude: пароль набирается с клавиатуры). Войдите на сервер и выполните там вторую строку, вместо `ЛОГИН` — свой логин латиницей:

```
ssh crm
printf '%s:%s\n' ЛОГИН "$(openssl passwd -6)" | sudo install -m 640 -o root -g www-data /dev/stdin /etc/nginx/test-app.testblacklist.ru.htpasswd
```

`openssl` попросит пароль дважды (`Password:`, `Verifying - Password:`), на экране он не виден. Новый пароль действует сразу, перезапускать ничего не нужно. Команда заменяет файл целиком: остаётся один логин.

**Вход на стенде.** Ссылка из письма ведёт на тот адрес, где её запросили: со стенда — на `test-app.testblacklist.ru`, с прода — на `app.testblacklist.ru`. Кука входа ставится только на свой адрес, без общего домена `testblacklist.ru`: вход на стенде не входит на прод, и наоборот. Письма настоящие, уходят со своим ключом Resend. Других внешних сервисов у приложения пока нет.

**База — копия прода.** Её заполняет последний бэкап прода. Испортилась или нужны свежие данные — пересоздайте её из самого свежего бэкапа прода (запускаете вы, в своём терминале). Войдите на сервер и выполните там вторую строку:

```
ssh crm
bash /opt/personal-crm/staging/deploy/restore.sh staging $(ls -1 /opt/personal-crm/backups/*.dump | tail -n 1)
```

Скрипт покажет, каким файлом заменит базу стенда, и ждёт `yes`. Дальше сам: останавливает приложение стенда, удаляет базу стенда, создаёт её заново и загружает бэкап, применяет миграции той версии, что работает на стенде (бэкап мог быть снят при более старой), запускает приложение и проверяет `/health`. Копию прежней базы стенда он не снимает. Прод не трогает: бэкап прода только читается. Все входы на стенде после этого заканчиваются — войдите заново по ссылке. Самый свежий бэкап прода — ночной (`daily`) или снятый при последней выкатке прода, если она была позже (список — `ssh crm ls -lh /opt/personal-crm/backups`).

**Настройки** — `/opt/personal-crm/staging/.env`, права 600. Строки те же, что у прода (`deploy/server.env.example`), значения свои:

- `POSTGRES_USER=crm`, свой `POSTGRES_PASSWORD`, `POSTGRES_DB=crm_staging`;
- свой `BETTER_AUTH_SECRET`;
- `BETTER_AUTH_URL=https://test-app.testblacklist.ru`;
- `SMTP_URL` — со своим ключом API Resend (resend.com → **API Keys**, отдельный ключ для стенда с правом **Sending access**);
- `EMAIL_FROM=noreply@mail.crm.testblacklist.ru`, `OWNER_EMAIL` — как у прода.

Посмотреть, какие строки есть, не показывая значений: `ssh crm "cut -d= -f1 /opt/personal-crm/staging/.env"`.

**Память.** Приложению стенда можно не больше 512 МБ, базе — не больше 256 МБ: стенд не отнимет память у прода. У прода лимитов нет.

**Проверить, что работает:** `ssh crm curl -s http://127.0.0.1:3001/health` — ответ `{"status":"ok"}`.

**Логи** стенда — в журнале сервера, как у прода (раздел «Логи»): `ssh crm sudo journalctl CONTAINER_NAME=staging-app-1 -n 100 --no-pager`, база — `staging-db-1`.

**Откатить стенд** на предыдущую версию (только вручную):

```
ssh crm 'bash /opt/personal-crm/staging/deploy/deploy.sh staging $(cat /opt/personal-crm/staging/previous-image)'
```

Если образа этой версии на сервере уже нет (ошибка сразу после `==> Pulling`), перезапустите на GitHub выкатку стенда того коммита: **Actions** → **Deploy staging** → нужный запуск → **Deploy staging** → **Re-run this job**.

**Откат стенда и Deploy prod.** **Deploy prod** с пустым полем берёт версию последней удачной выкатки стенда по истории на GitHub. Перезапуск старой выкатки стенда на GitHub попадает в эту историю — после него **Deploy prod** с пустым полем выкатит на прод именно эту, старую версию. Откат стенда по `ssh` в историю не попадает — **Deploy prod** с пустым полем по-прежнему возьмёт версию последней выкатки стенда с GitHub.

**Nginx и сертификат.** Настройки сайта — `/etc/nginx/sites-available/test-app.testblacklist.ru.conf`: HTTP уводит на HTTPS, HTTPS спрашивает пароль и передаёт запросы приложению стенда на `127.0.0.1:3001`. Сертификат Let's Encrypt — свой, с именем `test-app.testblacklist.ru`, продлевается сам (`certbot.timer`), после продления nginx перечитывает настройки. Проверить срок: `ssh crm sudo certbot certificates`.

## Бэкапы и восстановление базы

### Бэкапы

Бэкап — файл с копией всей базы: контакты, история мести, группы и сведения о том, какие миграции применены. Снимается сам, только на проде (на тест-стенде бэкапов нет):

- каждый день в 03:00 по Москве;
- при каждой выкатке на прод, до миграций, — в том числе при откате;
- при восстановлении базы — копия той базы, которую восстановление заменит.

Лежат на сервере в папке `/opt/personal-crm/backups`, читать их может только владелец. Имя файла — когда снят, зачем и при какой версии приложения:

```
2026-11-03_14-05-22_deploy_65dc137f8a1e….dump
```

- `2026-11-03_14-05-22` — дата и время по Москве;
- `daily` — ежедневный, `deploy` — снят при выкатке, `before-restore` — перед восстановлением;
- `65dc137f8a1e…` — версия приложения, которая работала в этот момент: полный номер коммита. При выкатке это версия, которая стояла до неё. Первые 7 знаков совпадают с номером коммита на GitHub (на странице PR и в списке коммитов `main`).

Хранятся по 7 последних: 7 ежедневных и 7 бэкапов выкаток. Новый бэкап удаляет самый старый того же вида. Копии `before-restore` сами не удаляются — лишние удалите руками (`ssh crm rm /opt/personal-crm/backups/<имя файла>`).

**Ежедневный бэкап** снимает таймер systemd `personal-crm-backup.timer` на сервере, он запускает `deploy/backup.sh`. Таймер ставит и обновляет сама выкатка на прод — руками ничего настраивать не нужно. Время 03:00 по Москве записано в самом таймере и не зависит от часового пояса сервера. Если сервер был выключен в 03:00, бэкап снимется сразу после включения. Если в это время идёт выкатка или восстановление базы прода, бэкап ждёт их до 30 минут.

Когда был последний и когда будет следующий (`LAST` и `NEXT`, время сервера):

```
ssh crm systemctl list-timers personal-crm-backup.timer
```

Как прошли последние бэкапы — журнал сервера: `BACKUP SUCCEEDED (prod): <файл>` или `BACKUP FAILED (prod): <причина>`:

```
ssh crm sudo journalctl -u personal-crm-backup --since -3days --no-pager
```

Если ежедневный бэкап не получился, никто об этом не сообщает — ошибка есть только в журнале. Снять бэкап прямо сейчас, не дожидаясь ночи (команда ждёт, пока он закончится):

```
ssh crm sudo systemctl start personal-crm-backup.service
```

Бэкапы лежат на том же сервере, что и база: если пропадёт сервер, пропадут и они. Скачать бэкап к себе на компьютер:

```
scp crm:/opt/personal-crm/backups/<имя файла> .
```

Посмотреть, какие бэкапы есть:

```
ssh crm ls -lh /opt/personal-crm/backups
```

### Восстановление базы из бэкапа

Восстановление заменяет всю базу прода содержимым бэкапа: всё, что добавили или изменили после того, как бэкап был снят, пропадёт (но останется в копии `before-restore`). Запускаете только вы, вручную.

1. Войдите на сервер и выберите бэкап:
   ```
   ssh crm
   ls -lh /opt/personal-crm/backups
   ```
2. Запустите восстановление, указав файл:
   ```
   bash /opt/personal-crm/deploy/restore.sh prod /opt/personal-crm/backups/<имя файла>
   ```
3. Скрипт проверит, что файл — настоящий бэкап (иначе остановится, ничего не изменив), и покажет:
   - `Backup file` — каким файлом заменит базу: путь, размер, когда снят и при какой версии;
   - `Database` — какую базу заменит и её текущий размер;
   - `App version` — какая версия приложения работает; она не изменится.

   Если версия бэкапа и работающая версия разные, будет предупреждение `WARNING` с двумя командами — о них ниже.
4. Наберите `yes` и нажмите Enter. Любой другой ответ — отмена, ничего не меняется (`Cancelled. Nothing was changed.`).
5. Дальше скрипт сам:
   - снимает копию текущей базы (`before-restore`);
   - останавливает приложение — сайт на это время не открывается;
   - удаляет базу, создаёт её заново пустой и загружает в неё бэкап — целиком или ничего;
   - запускает приложение той же версии и проверяет, что `/health` отвечает 200.

В конце — строка `RESTORE SUCCEEDED` и путь к копии прежней базы.

**Если версия бэкапа другая.** Бэкап выкатки снят при версии, которая работала до неё. Если после неё в базе что-то поменялось (новые таблицы или поля), приложение текущей версии на восстановленной базе может не работать. Тогда выберите одно из двух — команды скрипт печатает в предупреждении:

- вернуть приложение той версии, при которой снят бэкап: `bash /opt/personal-crm/deploy/deploy.sh prod ghcr.io/ttaktashova/personal-crm:<версия бэкапа>`;
- оставить текущую версию и довести восстановленную базу до неё: `bash /opt/personal-crm/deploy/deploy.sh prod ghcr.io/ttaktashova/personal-crm:<текущая версия>` — скрипт выкатки снова применит миграции, данные из бэкапа останутся.

На сервере хранятся образы за последние 2 недели, а более старые — только текущей и предыдущей версии прода и текущей версии тест-стенда (раздел «Чистка старых образов»). Если нужной версии там нет и скачать её скрипт не смог (ошибка сразу после `==> Pulling`), выкатите её через **Deploy prod**, вписав номер в поле **Version** — если она проходила тест-стенд и есть среди 10 последних сборок в GHCR.

**Если восстановление упало.** Скрипт ничего не откатывает сам. До ответа `yes` и при ошибке на копии текущей базы ничего не меняется. Если шаг упал после остановки приложения, приложение остаётся остановленным, а скрипт пишет `RESTORE FAILED (prod)`, на каком шаге, где лежит копия прежней базы и команду, чтобы вернуть её тем же `restore.sh`. Если база восстановлена, но приложение не ответило на `/health`, — `RESTORE FAILED (prod): the database is restored, but the app did not pass the smoke check`.

## Как устроено

- `src/app` — страницы: список контактов (`page.tsx`), карточка (`contacts/[id]`), сохранение и удаление контактов (`contacts/actions.ts`) и записей о мести (`contacts/interaction-actions.ts`), вход (`login/page.tsx`, запрос ссылки — `login/actions.ts`), «Ссылка устарела» (`login/expired/page.tsx`), выход (`sign-out-action.ts`) и адреса библиотеки входа (`api/auth/[...all]/route.ts`: переход по ссылке из письма, проверка входа)
  - вход — по ссылке из письма, библиотека Better Auth (`src/lib/auth.ts`). Ссылка работает 15 минут и один раз, новая гасит старые; в базе лежит её хеш. Почта приводится к маленьким буквам без пробелов по краям. Не больше 3 писем на одну почту за 10 минут (`src/lib/sign-in-limit.ts`); письмо, которое не ушло, не считается. Первый вход новой почты создаёт пользователя и пять его групп: «Бывшие», «Должники», «Коллеги», «Не любят котиков», «Родственники» (`src/lib/starter-groups.ts`)
  - вход держится 30 дней с последнего захода на этом устройстве: при каждом открытии приложения браузер спрашивает `/api/auth/get-session` (`src/components/session-refresh.tsx`), и не чаще раза в сутки срок сдвигается. В шапке — почта и «Выйти»; выход заканчивает вход только на этом устройстве
  - письмо собирает `src/lib/sign-in-email.ts`, отправляет `src/lib/mail.ts` (Nodemailer) по адресу из `SMTP_URL`. Ни почта, ни ссылка в журнал не попадают: при сбое там только `Sign-in email failed (code …)`
  - главная показывает список по страницам: по алфавиту, по 50 человек. Над списком, в строке со счётчиком и перед «По: …», — переключатель «‹ 1 … 4 5 6 … 20 ›», текущая страница в нём выделена; на телефоне и в окне уже 768 px он стоит отдельной строкой под счётчиком. Поиск, счётчик и переключатель прилипают к верху экрана, пока листаешь список. В браузер уходит только одна страница, а не весь список
  - справа от счётчика — выбор «По: 25 · 50 · 100». Нажатие запоминается в этом браузере (cookie `contact-list-size`, в ней только число); ссылка с `?size=` показывает своё количество, но выбор не меняет. После смены количества открывается страница, где стоит первый контакт текущей страницы

Выбранная группа сужает и список (со страницами, поиском и счётчиком «12 контактов» / «Найдено: 3 из 12»), и блоки «Скоро день рождения» и «Пора мстить»; при смене группы открывается первая страница, поиск и количество остаются. Пустая группа показывает «В группе «…» пока никого нет». На телефоне группы прокручиваются вбок, на компьютере переносятся на следующую строку
  - группа — в адресе вместе со страницей, поиском и количеством: `/?group=3`, `/?group=3&q=петров&page=2&size=100` (в адресе номер группы, поэтому переименование его не ломает). Без `?group=`, с не числом или с уже удалённой группой показываются все. Выбор группы нигде не запоминается: главная, открытая заново без `?group=`, показывает всех
  - кнопка «Группы» открывает окно «Группы»: все группы по алфавиту с числом людей, поле «Новая группа» с кнопкой «Добавить» (или Enter), у каждой группы иконки «Переименовать» и «Удалить группу». Форма переименования и подтверждение удаления показываются внутри этого же окна, без второго окна поверх. Удаление группы людей не удаляет. Переименование и удаление группы не меняют дату «изменён» у людей
  - после «Добавить черта» открывается страница, на которой стоит новый контакт, с меткой «Новый»; группа и поиск при этом сбрасываются
  - «Весь список» в карточке и удаление контакта возвращают на ту страницу, с тем поиском, группой и количеством, откуда открыли карточку (запоминается во вкладке, `src/lib/list-return.ts`); карточка, открытая по прямой ссылке, ведёт на первую страницу
  - на главной кнопка «Добавить черта» открывает окно «Новый чертила»; отдельной страницы `contacts/new` больше нет, по этому адресу — «Контакт не найден»
  - на главной над поиском — блок «Пора мстить»: контакты с заданной частотой, которым ещё не мстили или с последней записи о мести прошёл срок (неделя — 7 дней, месяц, квартал и год — календарные, «сегодня» — по Москве). Сверху те, кому ещё не мстили, ниже — по сроку, при равном сроке — по алфавиту. Видно первых пятерых, остальные — по «+ещё N людишек»; при смене группы блок снова сворачивается до пятерых. У каждого кнопки «Отомстил» (запись с сегодняшней датой) и «Простить» (сбрасывает частоту); на телефоне это иконки. Мстить некому — вместо блока карточка «Пока некому мстить» с грустным котиком
  - над «Пора мстить» (или над карточкой «Пока некому мстить»), под строкой групп, — блок «Скоро день рождения»: у кого день рождения сегодня или в следующие 7 дней (сегодня 14 ноября — с 14 по 21 ноября; «сегодня» — по Москве). Считаются только день и месяц; у кого день рождения 29 февраля, в невисокосный год в блок не попадает. Сверху ближайшие, в один день — по алфавиту. В строке имя (ссылка на карточку) и подпись «сегодня · 14 ноября», «завтра · 15 ноября» или «через 3 дня · 17 ноября» — без года и возраста, кнопок нет. Видно первых пятерых, остальные — по «+ещё N людишек», как в «Пора мстить»; при смене группы блок снова сворачивается до пятерых. Ни у кого скоро нет дня рождения — блока нет совсем, под строкой групп сразу «Пора мстить». Блок приходит вместе с «Пора мстить», вместо одной заготовки, так что страница сдвигается один раз
  - карточка открывается в режиме просмотра; у имени две иконки: «Редактировать» открывает окно «Редактировать контакт», «Удалить» спрашивает подтверждение (удаляются контакт, заметки и история мести; группы остаются, даже если в них больше никого нет)
  - в окнах «Новый чертила» и «Редактировать контакт» после «Откуда знакомы» — поле «Группы»: из списка можно выбрать несколько групп, выбранные стоят метками с крестиками (по алфавиту), а набранный текст сужает список. Если такой группы нет, в конце списка — пункт «Создать группу «…»» (Enter выбирает подсвеченный пункт и форму не отправляет, Ctrl+Enter сохраняет). Новая группа появляется в базе только вместе с контактом: «Отмена» её не создаёт. Контакт и его группы сохраняются одной операцией: либо всё, либо ничего. Если выбранную группу удалили, пока окно было открыто, контакт сохранится без неё
  - в карточке после «Откуда знакомы» — строка «Группы» метками по алфавиту (все, сколько бы их ни было), без групп — «не указано». В списке под «Откуда знакомы» у человека видны до трёх меток и «+N» для остальных; длинное название обрезается, полное видно при наведении. «изменён» меняется при сохранении в окне «Редактировать контакт», в том числе если поменяли только группы
  - в окнах «Новый чертила» и «Редактировать контакт» после «Почты» — поле «Дата рождения» из трёх частей в одну строку: «День», «Месяц» (список «января» … «декабря»; первый пункт «Не указан» стирает месяц, пустой список показывает серую подсказку «Месяц») и «Год». Год можно не указывать. День и месяц указываются вместе, такая дата должна существовать (31 апреля — нет; 29 февраля без года — можно, с годом — только с високосным), год — четыре цифры не раньше 1900, дата — не позже сегодняшней по Москве. Иначе под полем одна ошибка («Укажите день и месяц», «Такой даты нет», «Год — четыре цифры, не раньше 1900» или «Дата рождения не может быть позже сегодняшней»), фокус на «День», окно не закрывается. Сервер проверяет теми же правилами (`src/lib/contact-schema.ts`), даже если запрос пришёл не из окна
  - в карточке после «Почты» — строка «Дата рождения»: «17 ноября 1990», без года — «17 ноября», без даты — «не указано». Смена или удаление даты рождения меняет «изменён», как любое поле
  - под именем — строка «мстили 24 октября 2026» или «Пока не мстили»; в списке полей — «Как часто припоминать» (раз в неделю, месяц, квартал, год или «Не задано»; задаётся в окнах «Новый чертила» и «Редактировать контакт») и раздел «Последняя месть»: последняя запись, ссылка «Вся история» и кнопка «Отомстил»
  - кнопка «Отомстил» открывает окно «Отомстил» с датой (по умолчанию сегодня по Москве) и текстом; «Вся история» открывает окно «История мести»: там же, внутри одного окна, добавление, изменение и удаление записей
  - записи о мести не меняют дату «изменён» у контакта; смена частоты (в том числе «Простить») — меняет

  - дата рождения контакта — три числа: `birth_day`, `birth_month`, `birth_year`. Год необязателен: пустой `birth_year` значит «год не указан», без выдуманного года-заглушки. Все три пустые — даты нет. База сама не пустит день без месяца, месяц без дня, год без дня и месяца и несуществующий день (30 февраля, 31 апреля; 29 февраля можно) — ограничение `contacts_birthday_check`. Остальное (29 февраля в невисокосный год, год не раньше 1900, дата не позже сегодняшней) проверяет приложение

Связи удаляются вместе с контактом или группой, сам контакт и сами группы остаются

Удаление пользователя удаляет его входы

  - миграции применяет `src/db/migrate.ts` (`applyMigrations`): все новые за раз — одной транзакцией, либо все, либо ни одной. Почту владельца из `OWNER_EMAIL` он кладёт в настройку базы `app.owner_email` на своём соединении — так её видит SQL миграции `0008`. Через него идут `pnpm db:migrate` и тестовые базы; в рабочем образе то же делает `scripts/migrate.mjs`

Если запрос не удался, в журнал приложения пишется `Database query failed: <запрос> (code …)`, например `Database query failed: createContact (code ECONNREFUSED)`: какой запрос, код ошибки и, если база их назвала, имена таблицы, поля и ограничения. Данных контактов, текста запроса и пояснений базы в записи нет. `code ECONNREFUSED` значит «база не отвечает»

Без почты владельца или с неправильной почтой `0008` останавливается с ошибкой `OWNER_EMAIL is not set or is not an email`, и ни одна миграция этого запуска не применяется; `0009_require_owner.sql` делает владельца обязательным: контакт или группу без владельца база больше не пустит; `0010_add_birthday.sql` добавляет контактам дату рождения (`birth_day`, `birth_month`, `birth_year`, у всех прежних контактов пустые) и ограничение `contacts_birthday_check`; прежние данные не меняет, так что прошлая версия приложения с такой базой работает

- `.github/workflows/ci.yml` — проверки на каждый PR в `main`
- `.github/workflows/deploy-staging.yml` — **Deploy staging**: после влития в `main` сборка образа и выкатка на тест-стенд
- `.github/workflows/deploy-prod.yml` — **Deploy prod**: выкатка на прод и откат, запускается только руками
- `.prettierrc.json`, `.prettierignore` — настройки Prettier: как оформлять код и какие файлы не трогать

Данные читаются и сохраняются только на сервере; браузер к базе напрямую не обращается.

Каждый видит и меняет только своё. Это проверяется в трёх местах:

- `src/proxy.ts` — быстрая проверка без базы: нет куки входа — сразу страница входа. Не трогает страницы входа, адреса `/api/auth/…` и `/health`. Это не защита: кука может быть устаревшей;
- `src/lib/session.ts` — настоящая проверка по базе: `requireUser()` возвращает вошедшего пользователя или уводит на страницу входа. Её вызывает каждая страница с данными и первой строкой каждое серверное действие: действие можно вызвать напрямую, мимо страниц;
- функции данных в `src/lib/` (`contacts.ts`, `groups.ts`, `interactions.ts`, `keep-in-touch.ts`, `birthdays.ts`) — первым параметром владелец, и каждый запрос отбирает только его строки. Забыть владельца нельзя: без него код не соберётся. Чужой контакт, запись или группа отвечают так же, как удалённые: «не найден».
